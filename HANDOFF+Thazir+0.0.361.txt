3. NEW DESIGN (all steps build on this; do not change names without a reason in CHANGELOG)
--------------------------------------------------------------------------------
Native (Kotlin):
- NEW file DlParts.kt: object DlParts { fun enabled(): Boolean (pref dp_on); fun run(item: DlItem): Boolean; fun abort(item: DlItem); fun clean(id: Int); fun snapshot(id: Int): List<Double>? ; own executor for part workers (NOT Downloader.pool: only 3 threads, they run the coordinators) }.
- run(item) returns TRUE = whole file is complete in Downloader.partFile(item.id) (caller then goes on to finish() as today); FALSE = parts mode not usable (setting off, POST, not http(s), no Range support, size unknown, file smaller than min size, Content-Encoding present, not enough disk, any failure) = caller runs the OLD single-connection code unchanged. Throws IOException when the user paused / cancelled (Downloader.run already stops silently on that).
- Final fallback = the old code. Stage list: 1) parts, 2) old single connection (already exists).
- Probe: one GET with Range "bytes=0-0": need 206 + Content-Range total (> 0) (or HEAD with Accept-Ranges: bytes + Content-Length); validator = ETag or Last-Modified (not weak "W/").
- Data file: files/dl/<id>.pp (preallocated RandomAccessFile / FileChannel, workers write at their offsets, 64 KB buffers). State file: files/dl/<id>.pp.json = {"v":1,"url","total","validator","n","parts":[{"s":start,"e":end,"d":doneBytes},...]} (saved about every 1 s and on pause). When all parts are full: rename .pp -> Downloader.partFile(id) (the old .part) so finish() / publish() stay byte for byte unchanged. On any parts failure BEFORE completion: delete .pp + .pp.json and return false (old code starts from 0; never mix files).
- Request headers: reuse Downloader.open() (cookies, UA, Referer, headerProvider). open() gets 2 OPTIONAL params with defaults = old behaviour: rangeEnd: Long = -1L, track: Boolean = true (track=false: do not write item.call, DlParts keeps its own call list for abort). Visibility private -> internal. Nothing else in open() changes.
- Progress: item.received = sum of parts done, item.total = total (via DownloadsApi.change so listeners keep working).
- Prefs (SharedPreferences "mgb_ui"): dp_on (Boolean, default false), dp_n (Int, default 4; allowed 2,4,6,8,16), dp_min_mb (Int, default 8; smaller files use the single connection). All 3 keys go into the SettingsScreen RESET list (S3).
- Adaptive safety: HTTP 429 / 403 / 5xx or a part that gets 200 instead of 206 -> fewer connections for the rest (n -> n/2 down to 2), two bad rounds -> return false (old single connection). A global cap of 16 part workers over all running downloads.
- plainJobs() JSON gets OPTIONAL new fields only: "parts": [fractions 0..1 per part], "speed": bytes per second. Old fields stay as they are.
Engine (JS):
- bigfile.js: STAGES (ordered list) gets a NEW first entry ['parts', readParts]. readParts = first piece 0..CH-1 via readDirect to learn total (needs a real total from Content-Range and total >= 2*CH, else throw = next stage), then N workers take the next piece index from a queue, every piece through readDirect (fetchRetry inside), results stored by index, Blob assembled in order, progress = sum, same report() / setStats() path, label text "Video: 12 MB / 80 MB - 3 parts - 4 MB/s". Never hand over a half file (same rule as readAll). Old stages 'direct' and 'page', mgWholeFile and the old plain way stay exactly as they are.
- Setting partsN in shared.js DEFAULTS (default 1 = off; 2..8 = workers). chunkFile = false still switches ALL big-file stages off.
- S5: window.mgPartsFile(url,label) thin wrapper + a guarded hook in downloadFile() (only when partsN > 1 and FST.got == 0; null = old stream code).

9. OPEN / RISKS (known before any code)
--------------------------------------------------------------------------------
- Signed / one-time / cookie-bound links and some CDNs refuse Range or several connections: handled by fallback, but the server answer is NOT known until a device test.
- Many connections can trigger 429 / 403 on the same CDN: adaptive n + fallback; default stays OFF.
- Downloader.pool has only 3 threads (coordinators); part workers must use their own executor (S1) or parts would starve each other.
- DownloadsApi.load() currently deletes .part for non-resumable items: S2 must do the same for .pp / .pp.json or leftovers pile up in files/dl.
- Writing at random offsets into a preallocated file: if the app dies, the .pp file has holes: ONLY the state file tells what is really done (S2: state saved after the bytes are written, never before).
- Engine blobs are held in memory (existing design): parallel pieces do not add more memory than the sequential stage (all pieces are kept either way).
- Stage 'page' of bigfile.js is still NOT tested (older open item). The new engine stage 'parts' is also NOT tested on a live site until the device test.
- Flip to default ON later: DlParts.enabled() default (S1) + shared.js partsN default (S4), 1 line each.
