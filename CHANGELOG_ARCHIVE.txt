=== CHANGELOG_PREPEND_0_0_468.txt ===
0.0.468 (FIX: native WebView crash on pop-up heavy sites such as missav.live; crash-host guard)
- Base = 0.0.467 (Thazir-main). Changed files: app/build.gradle.kts (0.0.468), CrashGuard.kt, TabManager.kt
- WHY: crash report 0.0.466 / 0.0.467 (Android 16, WebView 157.0.8103.38): SIGSEGV null pointer in libwebviewchromium on the MAIN thread, 2 s after "page: start missav.live", no app frame. Same family as 0.0.451. The native frames have no symbols, so the exact Chromium function is unknown; this patch removes the app paths that are the most likely trigger and records what happens next.
- 1. onCreateWindow (TabManager): window.open of a pop-under site made the app build a complete WebView (profile, 10+ document-start scripts, 4 JS bridges) and destroy it again, several times a second, while Chromium was still starting the page. Now a window is refused (return false) when: the opener host is "risky" (below), another window was opened less than 1.5 s ago, or 2 pop-up tabs already exist. Normal single pop-ups (login windows) still open.
- 2. close() of a pop-up tab: our WebViewClient is replaced by a plain one (no app code runs from the dying page), the page is set to about:blank, destroy() waits 700 ms (was: next message). Normal tabs unchanged.
- 3. CrashGuard: remembers the host of the last page start of a NORMAL tab (disk, only when the host changes; cleared on onStop; never for private tabs). A start after a crash adds that host to a "risky" list (max 40). Risky host: pop-ups refused, no CosmeticFilter / SocialMode script injection during onProgressChanged. The page still loads. CrashGuard.clearRisky() forgets the list.
- 4. Breadcrumbs for the next crash report: Diag "popup opened" / "popup refused (why)" with the opener host, and "guard: crash while loading <host>". If the next crash report shows "popup opened" right before the crash, the pop-up path was the cause; if not, send the report and the cause is elsewhere (document-start scripts / WebMessageListener "*" or the page itself).
- COULD BREAK: a site that really needs a second pop-up within 1.5 s (rare); a risky host loses the early cosmetic filter.
- NOT tested: Gradle build (CI), device. Brackets of both files counted.
- DEVICE TEST: (1) open missav.live: pop-up ads do not open tabs (Diag shows "popup refused"), page stays open. (2) log in with Google / Facebook popup on any site: still opens. (3) crash it (force stop in front): next start = Home tab + toast, Diag shows "crash while loading missav.live". (4) tap the old tab: loads with pop-ups blocked.
- ROLLBACK: restore CrashGuard.kt, TabManager.kt from 0.0.467; appVersionName 0.0.467.

- How: new ExtApi3.kt (handlers "ext.<api>": installed extensions only, the built-in Media Grabber is untouched). (1) webNavigation, main frame only: TabManager hooks (onPageStarted, onPageFinished, doUpdateVisitedHistory, onReceivedError) call ExtApi3 which sends onBeforeNavigate + onCommitted, onDOMContentLoaded + onCompleted, onHistoryStateUpdated / onReferenceFragmentUpdated (in-page changes), onErrorOccurred. Only to extensions that have the "webNavigation" permission (others get nothing and no worker wake); stopped workers wake through the normal ExtApi.emitExt path. Private tabs, Home, extension pages and non-http pages send nothing. addListener(fn, {url:[...]}) filters (host / path / query / url Equals Contains Prefix Suffix, schemes, ports, urlMatches, originAndPathMatches) are applied in the shim. getFrame / getAllFrames answer for the main frame (frameId 0) only. (2) runtime.reload restarts the extension's worker. (3) search.query opens the default search engine in the current tab (default), the tab with tabId, or a new tab (NEW_TAB / NEW_WINDOW); needs the "search" permission; never navigates a private / Home / extension tab (a new tab is opened instead). (4) browsingData.remove / removeHistory / removeCache / removeCookies / removeDownloads / removeLocalStorage / removeIndexedDB / removeServiceWorkers / removeFileSystems / removeWebSQL / settings (permission "browsingData"): always shows a confirm box naming the extension and what will be deleted; Delete runs the same code as Settings > Delete browsing data (ClearData.apply), Cancel answers "The user denied this request.". history follows "since"; cookies / site data / cache are always all-time (Android limit, the box says so). Single-site deletion (origins) and passwords are refused with a clear error; formData / appcache / pluginData do nothing. (5) storage.sync / storage.local quota constants (QUOTA_BYTES, MAX_ITEMS ...) exist like in Chrome.
- Changed files: ExtApi3.kt (new), ClearData.kt (1 line: apply), ExtApi.kt (register line, allow-list rows, permission rows), TabManager.kt (4 hook lines), assets/shim/chrome-shim.js, HowToUse.kt, app/build.gradle.kts.
- CHANGED BEHAVIOUR: installed extensions with the webNavigation permission now get real events (before: events built from tab updates, no history / error events). An installed extension WITHOUT the permission that used webNavigation events before gets no events now (Chrome behaves the same). Built-in Media Grabber: unchanged (node check: identical members, old webNavigation kept).
- COULD BREAK: a stopped worker of an extension with webNavigation listeners now wakes on every page load of a normal tab (more battery; the report shows it). Event order: onCommitted is sent right after onBeforeNavigate (Thazir has no separate commit signal). Sub frames never send events (documented limit). runtime.getBackgroundPage (MV2) stays "not supported" (a WebView cannot hand out another WebView's window). Per-item sync quota (8 KB) is a constant only, not enforced.

0.0.428 (S3 FIX: Page theme parity for extension panels in a dark app)
- Why: video 2: the injected "Export to PDF" card was WHITE with invisible text, in Quetta it is dark. Thazir darkens a light page itself, but the page still says prefers-color-scheme = light, so a site that themes itself (ChatGPT "System") stays light and its extension reads "light" once at start.
- How: new ExtTheme.kt + assets/shim/theme-hint.js. At document start, in the page world, ONLY on the origins of installed extensions' content scripts, matchMedia('(prefers-color-scheme: dark)') answers true (light query false) when the app is dark AND Thazir shows this page dark (Dark pages ON, or the site rule is Dark; a site rule Original = no change). So the site switches to its real dark theme and sets html.dark. Also (app dark only): run_at document_idle waits for the page "load" event or 1.5 s, whichever is first (Chrome idle meaning); document_end stays on DOMContentLoaded.
- Switch: Settings > Extensions > "Match page theme": Auto (default) > On (always when the app is dark, ignores Dark pages) > Off (0.0.425 behaviour). Reset: key ext_theme is in the Settings "general" Reset list. Report center "Extension compat" shows the choice.

- CHANGED BEHAVIOUR: light app = nothing changes. Dark app + extension with content scripts: pages shown dark by Thazir report dark to the page's JS (only matchMedia JS answers, CSS @media is not changed). Idle content scripts of installed extensions may start up to 1.5 s later than before on slow pages (dark app only). Built-in Media Grabber and pages without extension origins: untouched.

0.0.427 (S2 FIX: Extension popup / options / extension tabs fit the phone)
- Why: video 2: the popup of "ChatGPT Exporter" was a whole desktop page (about 40 % scale) in the top-left of the 480 dp window. The popup has no viewport meta, and Thazir laid it out at about 980 px.
- How: new ExtFit.kt. A document-start script (only https://appassets.androidplatform.net/ext/<id>/... of an INSTALLED extension) adds a viewport meta at the phone width. After the page loads it is measured up to 3 times in 1.5 s; if the content is wider than the window (fixed desktop popup) the viewport becomes the measured width (max 900), so the page is scaled once. That width is kept per extension version + page (pref ext_fit_w), so the next open has no jump. A page with its own viewport meta is never changed. Popup window height now wraps the content (40 % to 80 % of the screen, never under 240 dp).
- Same logic for an installed extension page opened as a tab (script added in ContentInjector.addExtScripts, measuring from TabManager.onPageFinished).
- UI: Settings > Extensions > tap an extension > "Page width": Auto > Phone width > Desktop width (Desktop = old behaviour). Reset: keys ext_fit, ext_fit_w are in the Settings "general" Reset list; removed with the extension.
- Changed files: ExtFit.kt (new), ExtScreen.kt, TabManager.kt (1 line), ContentInjector.kt (1 hook), ExtListScreen.kt, SettingsScreen.kt (RESET), DiagMore.kt, HowToUse.kt, app/build.gradle.kts.
- CHANGED BEHAVIOUR: popups / options pages of installed extensions are laid out at phone width (before: 980 px for the popup). Built-in Media Grabber pages untouched (script only matches 32-letter a-p ids of installed extensions; ExtFit ignores everything else). If the document-start script is not supported the popup keeps the old wide page.
- COULD BREAK: a popup that is wider than the window and has its own tuned CSS (use Desktop width for it); popup that fills with content after 1.5 s may stay smaller than needed (it scrolls; min height 40 %).
- NOT tested: Gradle build (CI), device. Dynamic viewport change after load is assumed to relayout (Chrome WebView does).
- DEVICE TEST: 1) Settings > Extensions > ChatGPT Exporter, Page width = Auto. Open its popup from the menu: it must fill the width with readable text, window as high as its content. 2) Close and open it again: no jump in size. 3) Tap Page width to Desktop, reopen: old tiny look (proves the switch). 4) Phone width: full width. 5) Rotate the phone with popup open, then reopen. 6) Open the extension Options (extension tab and window): readable, no tiny page. 7) Media Grabber popup, Queue, Manga, History look exactly as before. 8) Settings > General > Reset to default: Page width choices go back to Auto.
- Rollback: delete ExtFit.kt and revert the hook lines (ExtScreen: fitOn, isInstPopup, hFit, fitHeight, ExtFit.onLoaded; TabManager 1 line; ContentInjector 1 line; ExtListScreen row; SettingsScreen RESET; DiagMore line).
